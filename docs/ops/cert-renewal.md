# Certificates

Two unrelated certificates, both of which stop the product working when they
expire, in different ways.

## TLS (the site)

Handled by whatever terminates TLS in front of nginx (Railway, a load
balancer, certbot). If it lapses, browsers refuse the site outright — and
because HSTS is set with `max-age=63072000`, they will refuse it for **two
years** for anyone who has visited before. Renew before expiry; there is no
"click through the warning" path once HSTS is in effect.

## The signing certificate (PAdES)

`SIGNING_CERT_PATH` / `SIGNING_CERT_PASSWORD`. This is the key every completed
envelope is sealed with.

- **Development uses a self-signed certificate**, generated by `up.sh`, and
  `/verify` says so in as many words. Production needs a real one from a CA, or
  an explicit decision to stay self-signed with that copy left in place.
- **Renewal does not invalidate old signatures.** A PAdES signature is valid
  for the moment it was made; what proves that moment is a timestamp from the
  TSA, which is why `TSA_URL` matters more than the certificate's remaining
  life. Without a TSA, an expired certificate makes old signatures
  unverifiable — set one before launch.
- Rotating: place the new `.p12`, update the two variables, restart api and
  workers. Envelopes completed under the previous certificate keep verifying,
  because the certificate chain travels **inside** the signed PDF.

## If the TSA is down

Sealing continues without a timestamp (PAdES B-B rather than B-T) rather than
failing the envelope — a signature nobody can complete is worse than one whose
timestamp has to be inferred from our audit trail. It is visible in
`/verify`'s output, and worth an alert rather than a silent downgrade.
